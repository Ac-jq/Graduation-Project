# 第 3 期设计前置文档

## 1. 文档定位

本文件是第 3 期“运营治理与数据闭环”的后端设计草案，只做设计预研，不写代码，不修改现有业务语义。

当前目标是为后续三块能力建立前置共识：

- 资源库模块
- 统计分析模块
- 管理员 AI 运维模块

## 2. 资源库模块设计草案

### 2.1 模块目标

围绕 PRD 中的“自助资源模块”，为学生提供可浏览、筛选、收藏的图文/音频/视频资源，为管理员提供资源管理能力。

### 2.2 建议拆分

| 子模块 | 职责 |
| --- | --- |
| 资源中心 | 学生侧资源列表、详情、标签过滤 |
| 收藏夹 | 学生侧收藏/取消收藏 |
| 资源管理 | 管理员上传、编辑、上下架 |
| 标签管理 | 管理员维护主题标签 |

### 2.3 建议数据模型

建议新增以下表：

| 表名建议 | 说明 | 关键字段建议 |
| --- | --- | --- |
| `resource_library_item` | 资源主表 | `title`、`summary`、`resource_type`、`cover_url`、`content_url`、`status`、`publish_time` |
| `resource_library_tag` | 标签字典 | `tag_code`、`tag_name`、`sort_no` |
| `resource_library_item_tag` | 资源与标签关系 | `item_id`、`tag_id` |
| `resource_library_favorite` | 学生收藏关系 | `user_id`、`item_id`、`created_at` |

### 2.4 接口建议

学生侧：

- `GET /api/resources`
- `GET /api/resources/{resourceId}`
- `POST /api/resources/{resourceId}/favorite`
- `DELETE /api/resources/{resourceId}/favorite`
- `GET /api/student/favorites/resources`

管理员侧：

- `GET /api/admin/resources`
- `POST /api/admin/resources`
- `PUT /api/admin/resources/{resourceId}`
- `POST /api/admin/resources/{resourceId}/publish`
- `POST /api/admin/resources/{resourceId}/unpublish`

### 2.5 设计约束

- 资源内容与标签关系应为多对多
- 学生只能维护自己的收藏记录
- 资源统计埋点要能为第 3 期统计分析模块复用
- 若接入 MinIO，建议资源元数据与文件对象地址解耦

## 3. 统计分析口径草案

### 3.1 统计目标

为管理端提供聚合级、脱敏级统计结果，不直接暴露学生个人明细。

### 3.2 建议优先指标

#### 3.2.1 使用度指标

| 指标 | 口径草案 |
| --- | --- |
| 日活用户数 | 当日产生任意有效登录或业务访问行为的去重用户数 |
| 测评完成数 | 当日提交量表会话数 |
| AI 会话数 | 指定周期内新建 AI 会话数 |
| AI 消息数 | 指定周期内 AI 会话消息总数 |
| 预约发起数 | 指定周期内创建预约单数 |
| 预约完成数 | 状态已到 `COMPLETED` 的预约数 |
| 资源浏览量 | 资源详情访问次数 |
| 资源收藏数 | 收藏动作总次数 |

#### 3.2.2 风险相关指标

| 指标 | 口径草案 |
| --- | --- |
| 高风险报告数 | `mental_scale_report.level_code = HIGH` 的报告数 |
| 高风险 AI 会话数 | `ai_chat_session.risk_flag = 1` 的会话数 |
| 高风险消息命中数 | `ai_chat_message.risk_level = HIGH` 的消息数 |

#### 3.2.3 维度建议

优先支持的统计维度：

- 学院
- 年级
- 性别
- 时间区间
- 量表类型
- 资源标签

### 3.3 输出边界

- 后台看板只展示聚合结果
- 导出报表不包含姓名、学号、账号、聊天明文
- 若某维度样本量过小，建议后续增加最小样本阈值，防止变相反查

### 3.4 技术建议

- 先做读时聚合，避免过早引入复杂数仓
- 若后期数据量增长，再考虑按日快照表或宽表优化
- 埋点源优先复用：
  - `sys_audit_log`
  - `mental_scale_report`
  - `ai_chat_session`
  - `ai_chat_message`
  - `consult_appointment`
  - 未来资源访问日志

## 4. 管理员 AI 运维三段式流程草案

### 4.1 目标

管理员 AI 运维不能直接“自然语言一句话改库”，而应遵守可审查、可回滚、可追踪的三段式流程。

### 4.2 三段式流程

#### 第一段：意图解析

输入：

- 管理员自然语言指令

输出：

- 结构化操作意图
- 影响对象范围
- 风险等级

示例：

- “帮我停用三个月未登录的学生账号”
  - 意图：批量禁用用户
  - 条件：角色=学生，最近登录时间为空或超过阈值
  - 风险：高

#### 第二段：待执行计划生成

AI 只生成计划，不直接执行。

建议输出内容：

- 操作类型
- 目标数据集过滤条件
- 受影响记录预估数量
- 字段变更前后对比
- 是否需要二次输入确认

建议前端以结构化清单呈现，例如：

| 项目 | 内容 |
| --- | --- |
| 操作对象 | `sys_user` |
| 过滤条件 | `role_code = STUDENT and last_login_at < ...` |
| 影响数量 | 28 |
| 变更字段 | `status: ACTIVE -> DISABLED` |
| 风险等级 | HIGH |

#### 第三段：人工确认执行

只有管理员显式确认后，系统才允许执行。

执行后必须记录：

- 操作人
- AI 解析原始文本
- 执行计划快照
- 最终执行结果
- 失败项
- 执行时间

### 4.3 建议后端边界

- AI 模块只负责解析和生成计划
- 真正执行仍走后台服务层和事务
- 所有执行都必须产生日志
- 暂不允许 AI 直接输出原生 SQL 给数据库执行

### 4.4 建议数据结构

建议新增：

| 表名建议 | 用途 |
| --- | --- |
| `admin_ai_operation_plan` | 存储 AI 生成的待执行计划 |
| `admin_ai_operation_execution` | 存储人工确认后的执行结果 |

## 5. 与当前代码的衔接建议

- 第 3 期优先复用现有角色、审计、通知、统一异常和统一返回结构
- 资源库、统计分析和管理员 AI 运维都不应破坏第 1 期、第 2 期已有接口语义
- 若要补统计口径，优先在设计文档阶段先锁定指标定义，再写接口，避免前后端口径漂移
